# Тестовое задание: Rust-разработчик — стаканы Binance + Aster

**Язык:** Rust (stable).

**Репозиторий:** ваш, публичный или приватный с доступом ревьюеру.

## Задача

Соберите небольшой сервис, который:

1. Поддерживает два независимых рыночных фида:
   - Binance order book — публичный WebSocket depth Binance;
   - Aster order book — публичный рыночный depth Aster / Asterdex.
2. Хранит оба стакана так, чтобы по ним можно было принимать решения.
3. Считает на их основе любой собственный торговый сигнал (см. ниже) — без реальной отправки ордеров.

Реальная торговля, подпись trading API, listen key аккаунта, вывод средств и приватные
эндпоинты запрещены. Для обоих фидов достаточно публичного market data.

## Источники данных — обязательно оба

### A. Binance order book

- Публичный рыночный стакан Binance: spot или USD-M futures — ваш выбор;
  зафиксируйте его в [README](../README.md).
- Одного символа, например `BTCUSDT` / `ETHUSDT`, достаточно.
- Нужен именно стакан: partial book, diff-stream + snapshot по документации Binance,
  а не BBO/ticker. Как синхронизировать snapshot и diff — ваш выбор.

### B. Aster order book

- Публичный рыночный стакан Aster (Asterdex): WebSocket depth-поток и при необходимости
  REST-снимок глубины по документации площадки.
- Ключи API / подпись для market data не требуются — подключайтесь к публичным URL.
  Типичная схема: WS combined stream вида `{symbol}@depth@…` и публичный HTTP depth snapshot.
  Аккаунтные и торговые API не используйте.
- Символ согласуйте с доступным на Aster рынком, например `ETHUSDT`;
  в [README](../README.md) укажите точные URL и имя потока.

Оба соединения должны быть отказоустойчивыми: обрыв сети, таймаут, закрытие со стороны
площадки, краткий «плохой» кадр не должны оставлять процесс в мёртвом состоянии без явного
сигнала. Reconnect / resubscribe / backoff / watchdog / resync книги — ваш выбор,
но поведение должно быть наблюдаемым: логи / метрики / статус по каждому фиду.

## Обязательный периметр

### 1. Горячий путь приёма

- Путь от получения кадра WS до обновления вашего внутреннего представления
  соответствующего стакана считайте горячим.
- Критерий: этот путь не должен быть завязан на тяжёлую или блокирующую работу
  «на каждый тик» без необходимости. Что вынести с горячего пути — ваш выбор.
- Два фида могут жить в разных задачах/потоках — или нет; это тоже ваш выбор.
  Важно, чтобы один медленный фид не делал второй «молча мёртвым» без явной модели.

### 2. Хранение данных

- Нужно консистентное представление обоих стаканов, из которого читает алгоритм сигнала.
- Одна структура на оба рынка, две отдельные, общий snapshot-слой — ваш выбор.
- Ожидается, что вы сможете коротко объяснить: кто пишет в каждый стакан, кто читает,
  что видит читатель при гонке с писателем, что происходит при дыре/ресинхроне
  на одном фиде, пока второй жив.

### 3. Алгоритм сигнала — без исполнения

- Придумайте любой математический / эвристический сигнал, который использует оба стакана:
  спред между площадками, дисбаланс, относительный mid, фильтр по свежести и т. д.
- Прибыльность не оценивается. Можно заведомо игрушечный сигнал.
- Алгоритм должен:
  - читать данные из вашего хранилища, не парсить WS повторно «сбоку»;
  - учитывать, что фиды независимы: разная свежесть, возможные разрывы;
  - периодически или по событию выдавать решение вида `Hold` / `Long bias` / `Short bias`
    (или свою шкалу) плюс краткое обоснование — числа из хранилища по обеим книгам.
- Исполнения ордеров нет: не вызывайте trading API даже «в dry-run».

Вопросы вида «какой Mutex правильный» лучше решить самостоятельно в коде и [README](../README.md).
