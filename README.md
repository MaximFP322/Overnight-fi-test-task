# Overnight Fi Test Task

Решение [тестового задания Overnight Fi](docs/test-task.md).

Сервис на Rust stable получает публичные стаканы BTCUSDT с Binance USD-M Futures
и Aster, поддерживает их локальное состояние и рассчитывает межбиржевой сигнал.

## Запуск

Для нативного запуска нужны Rust stable и `just`, для контейнерного Docker Compose.

```sh
just run         # нативно; остановка Ctrl+C
just run-docker  # сборка и запуск в Docker с логами в консоли
just stop-docker
```

Сборка через `just` использует release, `target-cpu=native`, fat LTO и один codegen unit.
Настройки фидов и стаканов задаются в `src/pipeline/config.rs` и конфигурациях
коннекторов; выбор стратегии — в `src/main.rs`.

## Источники данных

Оба фида используют поток `btcusdt@depth@100ms` и начальный snapshot до 1000 уровней
на сторону. Коннектор добавляет к REST URL параметры `symbol=BTCUSDT&limit=1000`.

| Биржа | WebSocket | REST snapshot |
|---|---|---|
| Binance USD-M | `wss://fstream.binance.com/public/ws/btcusdt@depth@100ms` | `https://fapi.binance.com/fapi/v1/depth` |
| Aster | `wss://fstream.asterdex.com/ws/btcusdt@depth@100ms` | `https://fapi.asterdex.com/fapi/v3/depth` |

## Архитектура

```text
Binance connector ─┐
                   ├─> Engine ──> Signal output ──> консоль
Aster connector ───┘       │
                           └────> Telemetry ──────> metrics.jsonl
```

- **Коннекторы Binance и Aster** получают WS-сообщения и REST-снимки, парсят данные,
  проверяют последовательность обновлений и отправляют события рынка и статусы в engine.
- **Engine** применяет события к двум стаканам и вызывает стратегию по обновлённому
  состоянию. При необходимости отправляет команду `Resync` нужному коннектору.
- **Signal output** читает решения стратегии и выводит их вместе с обоснованием в консоль.
- **Telemetry** получает готовые сводки метрик от engine, сохраняет JSONL и печатает статистику.

Каждый из пяти акторов работает на отдельном native-потоке в busy loop. Сообщения
передаются через ограниченные SPSC-очереди `rtrb`: inbox выбирает входящую очередь,
outbox направляет сообщение получателю. Обратные команды `Resync` также идут через SPSC.
Оба стакана принадлежат engine; стратегия читает их в том же потоке после применения события.
Одновременного чтения и изменения книги разными потоками нет.

У каждого фида свой статус и время последнего обновления. Во время reconnect/resync
одного фида второй продолжает обрабатываться. Коннекторы проверяют цепочку update ID,
совмещают snapshot с дельтами, используют backoff и таймаут чтения 60 секунд.
Engine также может запросить resync нужного фида. Supervisor управляет остановкой потоков;
неисправимая ошибка актора завершает весь pipeline с сообщением об ошибке.

## Стаканы и сигнал

Общий `OrderBook` предоставляет обновление уровней, best bid/ask, top-N и обход уровней.
По умолчанию используется `PagedOrderBook`: страницы по 64 ценовых тика с hash-индексом
и упорядоченным обходом. `BTreeOrderBook` альтернативная реализация на `BTreeMap`.
Цены и количества хранятся целыми числами в масштабе `10^8`; настроенный шаг BTCUSDT 0,1.
Хранится известная глубина из snapshot и последующих дельт, без ограничения top-N при обновлении.

`CrossVenueSpread` сравнивает исполнимые best-цены обеих бирж с порогом 1 bps:
`LongBias` соответствует покупке на Aster и продаже на Binance, `ShortBias` обратному направлению.
Если спред недостаточен, книга не синхронизирована, пуста или старше 5 секунд, результат `Hold`.
Возраст считается от последнего полученного обновления всей книги. Решение пересчитывается
по событиям; в лог выводится изменение направления или причины вместе с ценами и возрастом
обеих книг. Комиссии и исполнение сигнала не моделируются.

## Наблюдаемость и бенчмарки

Логи и сигналы выводятся в консоль. Метрики каждого запуска записываются в
`logs/<UTC-время>-<PID>/metrics.jsonl`; Docker сохраняет их в `logs` на хосте.
Сводка в консоли появляется раз в 10 секунд: msg/s, сигналы, resync, потери и p90/p99.
Гистограммы накопительные: парсинг, передача в engine, обработка и путь полученный frame → решение.
При завершении telemetry дочитывает свою очередь и сбрасывает файл.

```sh
just bench-orderbook --test  # быстрая проверка всех вариантов
just bench-orderbook         # Criterion: 84 варианта, прогрев 2 с, замер 4 с, 50 выборок
just bench-orderbook-allocs  # отдельный короткий подсчёт аллокаций
```

HTML-отчёт Criterion: `target/criterion/report/index.html`.
Чтение измеряется за один запрос обеих сторон, replay за весь набор дельт.

## Замер latency

Live-прогон Binance + Aster BTCUSDT от 01.11.2026: 600 секунд после первой синхронизации,
602 секунды всего, 9488 входящих сообщений engine и 34 сигнала.
Запросов resync от engine и потерь его исходящих сообщений нет.

Условия: AMD Ryzen 9 9950X3D, Linux x86_64 (ядро 7.0.0-38-generic), Rust 1.97.0.
Нативная release-сборка с `target-cpu=native`, fat LTO и одним codegen unit;
`PagedOrderBook`, пять busy-loop потоков без pinning.

| Участок | p50, мкс | p90, мкс | p99, мкс |
|---|---:|---:|---:|
| Парсинг в коннекторе | 10,2 | 14,3 | 20,5 |
| Передача из коннектора в engine | 1,5 | 2,9 | 10,2 |
| Полученный frame → начало обработки в engine | 11,8 | 15,9 | 23,6 |
| Обработка в engine: стакан и стратегия | 3,1 | 7,2 | 13,8 |
| Полученный frame → рассчитанное решение | 14,8 | 22,5 | 34,8 |

Процентили накоплены за весь запуск по HDR-гистограммам
с точностью одной значащей цифры. Полный путь измерен отдельной гистограммой,
процентили этапов не складываются. Начало отсчёта находится после получения готового
WS-сообщения: сеть и TLS/WS-декодирование исключены. Конец отсчёта предшествует
учёту метрик и отправке результата в outbox; доставка сигнала и вывод в консоль исключены.

## Возможные улучшения

Направления для дальнейших экспериментов. Выигрыш каждого изменения нужно проверять
на одинаковой нагрузке по задержке всей цепочки, включая p99.

1. **Приём данных через io_uring или TCP/IP-стек поверх DPDK.**
   `io_uring` позволяет организовать чтение через очередь завершений и сократить
   число системных вызовов, но требует подходящего цикла обработки I/O.
   Более радикальный вариант - пользовательский TCP/IP-стек поверх DPDK,
   например [F-Stack](https://github.com/F-Stack/f-stack), с интеграцией TLS и WebSocket.
   Сам DPDK не заменяет TCP/IP-стек. Текущие метрики начинаются после получения
   готового WS-сообщения, поэтому транспортный участок нужно измерять отдельно.

2. **Специализированный JSON-парсер под формат биржи.**
   Разбирать нужные поля и десятичные цены/количества напрямую из входного буфера,
   сокращая работу общего десериализатора, промежуточные структуры и аллокации.
   Сохранить корректную обработку поддерживаемых JSON-сообщений, включая перестановку
   и добавление полей. Результат сравнивать с текущим парсером на одинаковых сообщениях.

3. **Хранить стаканы в коннекторах, передавать в engine агрегаты.**
   Каждый коннектор владеет своим полным стаканом и после применения события
   публикует только данные, необходимые стратегии: best bid/ask, top-N,
   дисбаланс или другие агрегаты. Это сокращает объём данных между потоками.
   Для текущего сигнала достаточно best bid/ask, статуса синхронизации и времени
   последнего обновления. Свежесть и смену статуса нужно передавать даже тогда,
   когда best-цены не изменились. Состав агрегатов зависит от стратегии;
   стратегии, анализирующей отдельные дельты, потребуется более подробный поток.

4. **Обрабатывать приоритетную биржу и стратегию в одном потоке.**
   Например, в одном потоке читать WS Binance, парсить кадры, обновлять его стакан
   и вызывать стратегию. Aster остаётся отдельным коннектором со своим стаканом
   и передаёт через SPSC минимальные данные для расчёта. Так на пути Binance
   убирается межпоточная передача перед вызовом стратегии.
   REST-запросы вынести в отдельный актор с обменом через SPSC.
